### 9.2 Consent state machine — `ConsentStateMachine.cs`

```mermaid
stateDiagram-v2
  [*] --> NOT_SET
  NOT_SET --> GRANTED: member grants data_category
  GRANTED --> REVOKED: member revokes
  REVOKED --> GRANTED: member re-grants
  GRANTED --> PENDING_REAFFIRMATION: scope or policy change
  PENDING_REAFFIRMATION --> GRANTED: re-affirmed
  PENDING_REAFFIRMATION --> REVOKED: lapsed
  note right of REVOKED
    Reads fail closed.
    Revocation is immediate,
    never eventually consistent.
  end note
```

Constraint that makes this enforceable: `UNIQUE(member_id, data_category)` — one row per member per category, so "the current consent" is never ambiguous.

### 9.3 The four authorisation layers

```mermaid
flowchart TD
  R["Request + JWT"] --> L1{"L1 · authenticated?"}
  L1 -- no --> E401["401"]
  L1 -- yes --> L2{"L2 · policy allows this endpoint?"}
  L2 -- no --> E403["403"]
  L2 -- yes --> L3{"L3 · caller inside this family?"}
  L3 -- no --> E404["404 — existence itself is private"]
  L3 -- yes --> L4{"L4 · consent granted for data_category?"}
  L4 -- no --> E403A["403 + audit row"]
  L4 -- yes --> OK["Handler runs + audit row"]
```

Layer 3 returning **404 rather than 403** is deliberate: a 403 would confirm the family exists.
